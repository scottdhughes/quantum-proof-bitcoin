# Independent SHRINCS Stateless Recovery Verifier

## Status: INDEPENDENT DIFFERENTIAL PROTOTYPE - CONSENSUS DISABLED
## Spec-ID: SHRINCS-STATELESS-VERIFIER-ORACLE-v1
## Evidence-Updated: 2026-10-17
## Consensus-Relevant: NO

## Decision

Add a standalone C verifier for the complete 5,776-byte stateless recovery path of the pinned current SHRINCS draft and differentially test it against the draft executable model.

The verifier implements WOTS-TW, FORS, XMSS, the five-layer hypertree, the current draft's context encoding, and the binding of a stateless recovery signature to the stateful root in the 48-byte SHRINCS public key.

This prototype is not a production backend, consensus implementation, wallet signer, or full dual-mode SHRINCS parser. It remains under the project release hold.

## Verified Surface

`contrib/shrincs-ref/stateless_verify.c` independently performs:

1. exact 48-byte public-key and 5,776-byte signature length checking;
2. current-draft context serialization;
3. stateful-root binding inside the stateless recovery message;
4. the nested stateless message hash and 32-byte digest derivation;
5. FORS digest, 36-bit tree index, and 9-bit leaf-index extraction;
6. WOTS-TW message checksum and 35-chain public-key recovery;
7. ten-tree FORS authentication and root compression;
8. nine-level XMSS authentication;
9. five-layer hypertree traversal;
10. comparison with the public key's 16-byte stateless root.

The implementation uses the SHA-256 implementation pinned through `libshrincs`, but its WOTS-TW, FORS, XMSS, hypertree, message binding, and parser logic are independently written for PQBTC.

## Differential Corpus

The deterministic corpus contains two complete recovery signatures under one stateless-only key:

| Vector | Message/context mode | Randomization |
| --- | --- | --- |
| `stateless_deterministic_empty_context` | 32-byte message, empty context | deterministic draft mode |
| `stateless_fixed_randomizer_context` | 47-byte message, nonempty context | fixed 16-byte test randomizer |

The normal workflow run generates the two signatures from the pinned draft, verifies them with both implementations, and retains the exact vector bytes and SHA-256 identifiers as an artifact.

The rejection contract requires:

- every one-bit mutation of the first 5,776-byte signature: 46,208 cases;
- 96 targeted one-bit mutations across all structural regions of the second signature;
- every one-bit mutation of the first 48-byte public key: 384 cases;
- twelve length, message, and context negatives across the two vectors.

The same retained vectors are then verified under ASan/UBSan so the expensive Python key generation and signing are not repeated.

Both runs additionally require fourteen native ABI checks: a valid baseline;
null public-key and signature pointers; zero, short and long key lengths;
zero, stateful-sized, short and long signature lengths; null message/context
pointers with positive lengths; and oversized messages/contexts. Rejections
must return exactly zero, and the ordinary verifier ABI must return only zero
or one. These checks are part of the committed harness, not an external receipt.

Before importing the draft model or invoking the native library, the harness
validates the frozen manifest and both exact upstream checkout roots and pins.
It compares tracked source bytes to the pinned Git blobs, including files hidden
by index flags, and rejects staged, untracked and ignored source additions.
The source loader neither consumes nor creates cached Python bytecode.

Retained JSON is bounded to 64 KiB and must contain the exact two ordered cases,
their fixed message/context/randomizer metadata, the shared public key, exact
serialized lengths and matching per-vector byte hashes. These hashes detect
corruption; they are not authentication or immutable committed KATs. Observed
campaign totals must match the frozen manifest, and all native checks must pass,
before a new corpus or a PASS result is published. Failed campaigns do not
create or overwrite a corpus output.

## Independence Boundary

The C verifier:

- does not call the draft verifier;
- does not import the draft's WOTS-TW, FORS, XMSS, or hypertree functions;
- reconstructs all roots and indexes from the serialized signature;
- shares only pinned SHA-256 code with `libshrincs`.

The valid signatures are still generated by the pinned draft signer. This establishes a second implementation line for stateless verification, not independent construction design, security proof, or external cryptographic review.

## Security Limitations

This tranche does not establish:

- one strict project-owned parser combining stateful and stateless modes;
- committed immutable full-profile KATs;
- maximum-depth or full-block resource envelopes;
- sustained fuzzing or allocation-failure testing;
- formal correctness of the new C verifier;
- side-channel or fault properties of a signer;
- monotonic wallet-state safety;
- transaction sighash and chain-domain separation;
- consensus suitability;
- production readiness.

The research verifier uses bounded dynamic allocation for the contextualized message hash. A production-shaped verifier should accept a fixed transaction digest rather than arbitrary messages, eliminate or strictly encapsulate allocation, expose exact work accounting, and undergo independent code and cryptographic review.

## Validation

The dedicated workflow:

```text
.github/workflows/shrincs-stateless-oracle.yml
```

performs exact upstream checkouts, builds the independent C verifier, generates deterministic recovery vectors, runs the differential and mutation corpus, repeats with sanitizers, and retains the vectors as an artifact.

Local upstream execution uses disposable, network-disabled, nonprivileged tooling
containers with read-only source/root mounts, temporary builds and one owned
artifact-output mount. This containment is local test infrastructure, not a
published node image or evidence of production isolation. The hosted workflow
runs on its dedicated ephemeral runner; do not infer the local container's
boundary from hosted CI alone. PR/synthetic-merge and trusted-main receipts
remain separately bound to their actual runtime revisions.

The repository-level safety controls remain:

```text
consensus_enabled = false
production_backend = NONE
release_hold = true
```

## Strongest Next Attack

After this tranche passes, the strongest next engineering step is a single strict full-SHRINCS verifier envelope that dispatches only between the two modes of the same pinned scheme:

1. exactly 5,776 bytes selects stateless recovery;
2. the canonical 554-through-4,618-byte stepped range selects stateful verification;
3. every other length fails before hashing;
4. no ECDSA, Schnorr, rc2, or ML-DSA fallback exists;
5. committed KATs cover both modes;
6. exact parser and SHA-256 work limits are measured;
7. the implementation remains outside node consensus until review gates pass.

In parallel, work must begin on the monotonic crash-safe signer state machine. The stateless fallback protects seed restoration, but it does not make unsafe stateful signing acceptable.
