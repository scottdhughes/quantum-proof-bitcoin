# Independent SHRINCS Stateful Verifier Oracle

## Status: INDEPENDENT DIFFERENTIAL PROTOTYPE - CONSENSUS DISABLED
## Spec-ID: SHRINCS-STATEFUL-VERIFIER-ORACLE-v1
## Evidence-Updated: 2026-08-16
## Consensus-Relevant: NO

## Decision

Add a standalone C verifier for the complete stateful path of the pinned current SHRINCS draft and differentially test it against the draft executable model.

The verifier uses the qualified `libshrincs` WOTS+C and tweakable-hash primitives. The surrounding FXMSS parsing, message binding, authentication-path traversal, and 48-byte-public-key validation are implemented independently in `contrib/shrincs-ref/stateful_verify.c`.

This prototype is not a production backend, consensus implementation, wallet signer, or full SHRINCS verifier. The stateless path remains unimplemented.

## Verified Surface

The C verifier independently performs:

1. strict 48-byte public-key length checking;
2. stateful signature range and structural-length checking;
3. 64-bit leaf-index parsing and position validation;
4. stateful leaf depth and height recovery from the signature length;
5. current-draft context and stateless-root message binding;
6. current-draft `H_msg_sf` computation;
7. WOTS+C public-key recovery through the qualified libshrincs component;
8. FXMSS authentication-path reconstruction;
9. comparison against the 16-byte stateful root in the public key.

The prototype supports the current draft's full stateful signature range of 554 through 4,618 bytes, but this initial differential corpus exercises bounded small trees so vector generation remains fast and auditable.

## Differential Corpus

The deterministic corpus contains seven valid signatures:

| Structure | States |
| --- | --- |
| UXMSS depth 4 | 0, 1, 3, 4 |
| BXMSS depth 3 | 0, 3, 7 |

The corpus covers:

- minimum and increasing UXMSS path lengths;
- the terminal UXMSS leaf;
- balanced-tree first, middle, and final leaves;
- empty and nonempty contexts;
- 48-byte combined public keys;
- complete current-draft stateful signature serialization.

The workflow requires the independent C verifier to accept all seven signatures produced by the pinned draft and reject:

- all 32,688 one-bit signature mutations;
- all 2,688 one-bit public-key mutations;
- 42 structural or binding negatives, including truncation, extension, wrong messages, and wrong contexts.

The vectors and their SHA-256 identifiers are retained as a GitHub Actions artifact. They are not yet committed as a repository KAT corpus, so the project-wide `independent_kats` gate remains false.

## Independence Boundary

The implementation is independent at the FXMSS/stateful-verifier layer:

- it does not call the draft verifier;
- it does not import the draft's FXMSS functions;
- it recomputes the message digest and Merkle path in C;
- it uses only the separately qualified libshrincs WOTS+C and low-level hash APIs.

The test vectors are still generated by the pinned draft signer. This establishes differential implementation evidence, not independent construction design or external cryptographic review.

## Security Limitations

This tranche does not establish:

- correctness or compatibility of the stateless FORS/hypertree path;
- a complete full-SHRINCS parser shared by both modes;
- signer state safety;
- constant-time or side-channel properties of signing;
- worst-case maximum-depth resource envelopes;
- formal correctness of the new FXMSS C code;
- proof review for the selected construction;
- transaction sighash or domain separation;
- consensus suitability;
- production readiness.

The C verifier is a research oracle with bounded message size and uses dynamic memory for digest construction. A production-shaped verifier must remove or tightly bound that allocation, freeze the exact outer transaction envelope, add sustained fuzzing, and undergo independent review.

## Strongest Next Attack

The next cryptographic implementation tranche is the stateless path:

1. independently implement WOTS-TW, FORS, XMSS, and the five-layer hypertree verifier;
2. freeze and commit complete stateful and stateless KATs;
3. combine both paths behind one strict full-SHRINCS parser;
4. add adversarial resource measurements and sustained fuzzing;
5. only then begin a separate, disabled transaction-envelope proposal.

In parallel, the stateful signer must be developed as a monotonic crash-safe state machine. Verification progress does not reduce the signer-state requirement.
