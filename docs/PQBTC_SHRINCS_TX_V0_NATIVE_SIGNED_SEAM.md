# PQBTC SHRINCS-v0 native signed seam

Status: research-only, consensus-disabled, test-only.

This tranche composes the native Bitcoin Core transaction envelope from
`src/script/shrincs_tx_v0.cpp` with the project-owned strict dual-mode SHRINCS
research verifier. It does not wire either component into Script, consensus,
policy, wallet, RPC, mining, descriptors, PSBT, or a release binary.

## Stack and purpose

This work is stacked on the native transaction-parity tranche. Its only purpose
is to prove that the exact 32-byte digest produced from Bitcoin Core's native
transaction types is accepted by the independently reproduced SHRINCS verifier
for both current-draft modes:

- a 554-byte stateful signature at depth 1; and
- a 5,776-byte stateless recovery signature.

The shared verifier entry point remains:

```c
int pqbtc_shrincs_verify(
    const uint8_t *public_key,
    size_t public_key_len,
    const uint8_t *signature,
    size_t signature_len,
    const uint8_t *message,
    size_t message_len,
    const uint8_t *context,
    size_t context_len);
```

There is no algorithm registry, classical fallback, unknown-algorithm path, or
runtime negotiation. Serialized signature length selects only one of the two
modes of the same frozen SHRINCS profile.

## Native rejection corpus

The Boost suite requires both retained signatures to reject after every one of
these changes:

- 22 transaction-surface mutations, each checked against both modes;
- input-index mutation, checked against both modes;
- chain-ID mutation, checked against both modes;
- signing-context mutation, checked against both modes;
- one signature-bit mutation in each mode;
- public-key reveal/commitment mismatch in each mode; and
- cryptographic verification under a different committed key in each mode.

Total required rejections:

```text
22 * 2 + 2 + 2 + 2 + 2 + 2 + 2 = 56
```

## Build isolation

The signed seam is disabled by default:

```text
PQBTC_ENABLE_SHRINCS_SIGNED_SEAM_TESTS=OFF
```

The dedicated workflow explicitly enables it and supplies a checkout of the
pinned libshrincs commit:

```text
53bedb2c4be6b0dcc0a16fee665339d4f7e4e5b5
```

Only the test target then receives:

- `contrib/shrincs-ref/full_verify.c`;
- `contrib/shrincs-ref/stateful_verify.c`;
- `contrib/shrincs-ref/stateless_verify.c`; and
- pinned libshrincs `wots.c`, `thash.c`, `sha256.c`, and `util.c`.

Ordinary builds do not require or compile these research verifier sources.

A focused local invocation is:

```bash
cmake -S . -B build -G Ninja \
  -DBUILD_TESTS=ON \
  -DENABLE_WALLET=OFF \
  -DENABLE_IPC=OFF \
  -DPQBTC_ENABLE_SHRINCS_SIGNED_SEAM_TESTS=ON \
  -DPQBTC_LIBSHRINCS_SOURCE_DIR=/absolute/path/to/pinned/libshrincs

cmake --build build --target test_pqbtc --parallel 2
build/bin/test_pqbtc --run_test=shrincs_tx_v0_signed_seam_tests
```

## What this establishes

Subject to the retained corpus and the compiled research verifier, this shows
that native Bitcoin Core transaction serialization and hashing reproduce the
same signed digest used by the pinned SHRINCS draft and that both current-draft
signature modes verify through the independent C implementation.

It does not establish formal correctness, cryptographic security, consensus
suitability, production resource policy, signer-state safety, side-channel
safety, fault safety, or activation readiness.

The controlling state remains:

```text
consensus_enabled = false
production_backend = NONE
release_hold = true
```
